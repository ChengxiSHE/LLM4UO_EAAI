## Figure-level argument

The figure answers how benchmark failures become versioned modeling knowledge
without allowing the knowledge proposer to redefine its own correctness
boundary. Its conclusion is that construction is a bounded library transition:
an untrusted producer proposes a typed program, retained counterexamples reduce
a declared finite version space, a trusted checker admits only artifacts with
declared semantic and resource obligations, an exactly-one public router
preserves the old library outside unique coverage, and an independent endpoint
decides whether a new version is promoted.

The versioned library is the formal method state. The current experiments bind
its roles through distributed pinned code, plans and result closures rather
than one loadable canonical manifest. The final figure must not depict that
future manifest as an already implemented release artifact.

## Four-panel evidence architecture

| Panel | Visual question | Theory mapping | Claim boundary |
| --- | --- | --- | --- |
| a | What is the knowledge object, and which state is immutable? | Skill/library definitions; prefix-code and library-complexity interpretation | The proposer remains outside the trusted boundary |
| b | How do failures change the candidate space? | S1--S4.1: finite termination, finite-domain soundness, exact repair, monotone elimination and conditional balanced contraction | No logarithmic rate without balance; no claim of successful automatic recovery |
| c | What happens on an accepted, rejected or ambiguous input? | S5--S7 and S8.1: conditional accepted-path correctness, declared resource safety, exact fallback and conservative extension | No universal language proof or inside-coverage dominance theorem |
| d | What converts an admitted artifact into a library update? | S8, S8.2, S10, S10.1 and S10.2: correction-minus-regression accounting, modular gain, complexity-weighted candidate control and cumulative regression budgeting | Verifier acceptance is not benchmark utility; current runs did not use complexity-weighted promotion; cumulative guarantees require one fixed target |

The cross-panel loop is intentionally closed: an untrusted producer emits a
candidate; construction emits either a rejected witness or a content-addressed
skill; deployment records a durable output; promotion appends an immutable
successor or leaves the previous version unchanged. Rejection, ambiguity and
failed promotion must all have visible terminating paths.

## Visual semantics

The producer uses a dashed neutral outline. Trusted verifiers, endpoints and
sealed ledgers use dark solid boundaries. Candidate and admitted knowledge use
one method blue; accepted version transitions use restrained green; rejection
or observed regression reserves red; fallback and unchanged state use light
neutral grey. These meanings must remain consistent with the quantitative
result figure.

Formal software guarantees, assumption-conditional guarantees and empirical
decisions must be visually distinguishable. The final figure must explicitly
carry the labels `finite domain`, `conditional accepted-path correctness`,
`exact fallback`, `empirical benchmark gain`, and `risk budget`, together with
the boundaries `no universal natural-language proof`, `prospective
complexity-weighted promotion`, `fixed target required for cumulative bounds`
and `no unrestricted recursive self-improvement`.
