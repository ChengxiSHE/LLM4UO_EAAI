较低预算档若容不下首个完整请求的保守预留，会记录预算拒绝并保留分母。最高档必须容纳全部来源的初始请求，已列为独立预检项；这不保证复杂模型的所有后续修复都能在预算内完成。

目前没有可核验的该私有服务商费率，因而没有人民币硬上限。输入 token 采用完整请求 UTF-8 字节数加2,048的保守预留，另预留8,192输出 token；这不是对专有 tokenizer 或账单的证明。每次重试都是新的物理请求，单独预留并计入原有全局上限。服务商使用量缺失、计数不一致、超预留、模型名称改变、鉴权失败或账本损坏立即停止。瞬时网络错误及408/409/425/429/5xx按5秒、30秒退避，三次仍失败则隔离该请求；连续八次传输失败才全局熔断。已发出的超时请求仍可能计费。

## 研究口径与未决数据的固定处理

此次作了一个明确的协议选择：**完整基准采用“上游公开目标值/状态匹配”这一代理指标，独立参考模型核验另报。** 不再把“为所有公开基准重做专家 gold”当作运行公开参考比较的先决条件；也绝不把解析成功等同于独立认证。原有严格的 `evaluate_bound` 和旧审计状态未被放宽或覆盖，新代理评分有独立名称和实现。

- 1,243 条原生参考仍标为已解析、未独立认证；12条另有数值转录/证书及原生参考一致；96条解析未决。所有这些状态保留。
- ComplexOR 的参数元数据修订保持上一轮冻结版本；cut、fleet、net1、netmcol 四条输入歧义与 steel4 一条参考冲突保留为未决。没有猜测缺失数据或按照答案改模型。其余潜在题意问题保留审查注释，允许模型明确弃答。
- 只有有相应独立审计的 infeasible / unbounded 原生状态才可用于状态匹配。-1不自动解释为不可行。时间上限、未证明最优和未知不当成最优或匹配成功。
- LP、整数和混合整数线性模型走受控稀疏模型求解；非线性/锥约束、超出表示容量或缺失参数必须显式报告不支持/未决。**全量纳入不等于全数学类型均可求解。** 不把这些题线性化，也不从分母剔除。
- 每次评分在独立评价进程重新求解最终模型，不信任推理日志中自报的目标值。完整测试推理结束前，不向搜索器打开测试成绩。相同最优目标不证明模型或自然语言语义正确。

这是可执行的公开参考代理实验；不能把其结果表述为全题已由专家验证的建模正确率。论文的后续语义审计、额外基线或新增数学结构属于后续研究，不由“全量运行完成”自动推断为已完成。

## 自动流程与六种方法的区别

固定内核负责输入、求解、证据重放、写集合保护、回滚、费用和评分边界。可变程序只能对最多五个可选节点做一次局部插入、删除、移动、条件或作用域修改；不得包含题号、benchmark名称、答案、任意代码或评分规则修改。

Base只做初始建模；SolverRepair最多两次普通求解反馈修复；A使用固定teacher/差异证据/局部修复gate。B从普通修复流程出发，候选提出器看终端开发结果和错误类别；SimpleAB从A流程出发，使用同样的工具和证据汇总做普通程序搜索；Full另外获得共享前缀后实际两条分支的配对结果，按分歧前的证据特征组织纠错/退化反馈。

B的原子工具菜单与另两条搜索流相同，属于工具匹配的强控制，不是禁止接触任何语义操作的弱化基线。SimpleAB与Full具有同样的起始程序、最多六次调用、候选数、开发数据和选择规则。所有方法的基本角色提示和模型服务相同；不会因为某个组件已有就否定组合，也不把标准工具包装成首次创新。

每代先冻结全部方法/重复的候选，再打开任何该代验收结果；验收失败继承旧程序，成功才更新。最大两代后，程序永久冻结用于三个预算档的测试。没有真实API运行前，只能称为“已实现并离线验证的自进化流程”，不能称为已观察到进化收益。

## 验收与恢复

验收证据见 `results/full_preparation_verification.json`、`results/full_preparation_tests.txt` 和 `results/formal_stack_verification.json`。检查包括六种方法的36条真实数值求解/固定响应轨迹、提案→筛选→接受/拒绝→继承、前缀逻辑费用、缓存恢复、崩溃后续跑、有限重试、错误隔离、连续失败熔断、进度页面、token/JSON/权限保护、参考绑定、分母完整性、来源哈希和旧归档不变。

程序已修复一个恢复隐患：恢复执行时，条件只能看到已重放的前缀用量，不能因为账本已有后续调用而跳过原来的修复分支。数值工具结果按固定输入缓存并校验哈希；同一请求槽内容改变会停止，不能悄悄产生第二次费用。所有实际请求体、响应和失败保存在唯一私密运行目录，密钥不会进入记录。

断网会影响需要联网的模型请求：已完成并落盘的结果、工具缓存与账本保留；在途请求可能已经到达服务商，即使本地未收到结果也可能计费。请求超时设为90秒；没有有效使用量时保留该次完整预留。瞬时失败按冻结策略有限重试，耗尽后隔离当前单元并继续；持续故障由八次连续传输失败熔断。本地求解不依赖网络。

网络故障已与模型输出错误分开：初始建模、修复和流程提案中的基础设施中断直接传播到控制器，不保存为可评分的题目结果，不作为候选被拒绝的依据。开发评分拒绝这类记录，正式评价在读取缓存前也拒绝；旧格式中含网络失败的记录不能因保留了一个可求解模型而被算作成功，或因没有模型而被算作答错。受影响任务仍是未完成，不能删掉它来生成完整实验成绩。

控制器现在支持断点续跑。重启同一批准命令时，会校验并复用完整响应、推理文件、求解器缓存和流程进化检查点；进程死亡时仍处于reserved的请求保留完整预留，并消耗下一次有限重试。请求三次仍失败后写入基础设施不可用记录，正式矩阵保留该项但不把它算成模型错误；开发选择只比较共同可用样本，验收批次缺项则拒绝本次更新。进度同时写入 `progress.json` 和每20秒自动刷新的 `progress.html`。持久熔断和不可变性错误仍不得手工清除。

以上已用离线故障注入检查，包括DNS/连接错误、连接重置、超时、在途进程中断、重启禁止重发、提案中断和评分拒绝；没有读取实际密钥或发起实时API故障测试。修改前的Flash待确认方案保存在 `results/private/configuration_history/flash_before_network_guard/`，未批准、未运行；当前代码和协议须重新冻结验收后才能批准。

默认入口 `scripts/run_formal.py` 只做离线预检。批准工具还会核对当前计划哈希和最终验收报告；S1/S2授权均仍为completed。本次没有执行批准工具或实时模型调用。批准后运行同一入口的 `--execute-approved` 模式；恢复边界如上。服务商异常、资源耗尽或未知费用风险会按固定保护停止，不擅自换模型、加额度或开新账本。完整推理和评价成功后自动关闭本次授权。

## ARK 到底提供什么

**到目前为止，核心研究工作主要是用户和Codex完成的；ARK没有替我们证明方法有效，也没有实际贡献可测量的研究提升。** 使用ark-base环境不等于ARK研究引擎在运行。

本机ARK的价值是可选的外层编排：组织研究/开发/实验/写作角色，保存检查点，管理任务状态及论文产物。它的自主管理代理同样需要明确的问题、可靠评价和费用边界，还会增加独立API调用。对于本研究，外层自主代理继续重写方案反而会破坏冻结实验的可比性，因此本次不启动它。

真正的跨题流程搜索由本项目的受控运行器执行，不依赖ARK。后续若ARK能够省下任务管理、图表组织或论文整理的重复劳动，可以读脱敏汇总再使用；完全不用ARK也不影响本研究。详细边界见 `ark/FORMAL_RUN_BOUNDARY.md`。ARK是可选研究助理平台，不是这篇工作的算法贡献，也不是预算或安全的最终裁判。
