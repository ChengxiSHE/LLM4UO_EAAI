# 机制重设计阶段报告：从 v1 失败漏斗到 v9 可信编译确认

更新：2026-10-03。本报告记录正式实验之后按阶段执行的离线改进、反事实重放、受控机制验证、v4 开发 API 诊断，以及 v5/v6 冻结离线评价。只有第 5 节的 v4 诊断调用了模型 API；v5/v6 开发、冻结评价与盲审准备均没有新增 API 请求。

## 1. 阶段结论

原方案没有提升，首要原因不是求解器找不到差异，而是差异到安全动作之间发生了两次信号损失：v1 由模型填写大量可机械计算字段，导致反馈难以编译；放开机械瓶颈后，单一语义审查又会选择错误方向，数值 gate 无法区分“可执行”与“符合原文”。

当前已完成四轮机制迭代：

1. **v2 机械修复**：控制器确定引用位置并直接复制 teacher 片段；16k 预算不再进入必然失败的语义分支；solver repair 的无操作在再次求解前被拒绝。
2. **v3 候选选择**：控制器从求解器反例生成编号候选、编辑和局部行为测试，模型只选择候选、给出原文短引用或弃权。
3. **v4 保守双审查**：不再把模型生成的行名当作语义恒等标识；只允许双方具有同名行的局部修改，未对齐的增删行保持未决；主审与反方审查必须都选择 teacher 方向才允许修改。
4. **v5 候选独立语义合同**：对高置信、受限语法中的离散计数、占总量比例和库存—流量平衡，由控制器从公开原文和已声明接口生成规范约束与检查；合同可先修复初始模型，也可否决 teacher 的一致错误。完整模型不可安全求解时回滚并标记接口不足。

v4 的真实开发诊断没有通过门槛：两次一致审查接受了两个修改，但产生 0 次代理纠正和 1 次退化。v5 在相同 12 题的事后开发回放中得到 2 次纠正、0 次退化；扩展到全部 150 条开发角色记录时得到 3 次纠正、0 次退化，涉及两个 operational family。冻结后的 522 条锁定记录评价只有两个实际修改：一个前后都匹配标量代理，一个代理不可判定，因而预注册成功条件未满足。当前证据支持“安全方向选择在开发集改善”，不支持 benchmark 建模准确率提升。

## 2. 阶段 0：机械契约和预算路由

### 2.1 已完成改动

- 精确保留本地异常原因，不再把所有 `Invalid` 合并成一个类型名。
- 对唯一出现的原文引用由控制器确定字段、起止位置和哈希。
- 由控制器按已编译 edit 复制 teacher 片段，删除一次易失败的自由生成修复调用。
- 65,536 token 档才允许 v4 双审查；低预算轨迹保留当前模型并记录未触发原因。
- solver repair 在求解前规范化比较；无操作直接拒绝。v2 种子只保留一次普通 repair，因为正式轨迹中的第二次 repair 没有产生代理变化。
- 保留原 v1 运行时，新增版本化 v2/v3/v4/v5 路径；旧正式运行与账本语义不变。

### 2.2 旧响应重放

对正式账本中 2,730 个成功返回的唯一 teacher-feedback 响应进行只读重放：

| 编译路径 | 可编译 unresolved | 可编译 repair | 合计 |
| --- | ---: | ---: | ---: |
| 原 v1 严格协议 | 142 | 11 | 153 |
| v2 唯一引用重绑定 | 767 | 50 | 817 |

v2 把机械可用反馈提高到原来的 5.34 倍。50 个 repair 中 44 个通过原数值 gate；但开发角色上只有 2 个可判定代理转移，分别为 1 次纠正和 1 次退化，净值为 0。该结果说明格式修复是必要条件，不是效果充分条件。

## 3. 阶段 1：受控错误与 gate 验证

合成集包含 7 类单一错误，每类 5 个尺度，共 35 个正确修复和 35 个反向有害修改：缺失行、多余行、错误 RHS、错误系数、缺失整数性、过度整数性和目标方向反转。

- 确定性 edit 应用对 35/35 个正确方向实现精确恢复。
- 旧数值 gate 接受 35/35 个正确修复，同时也接受 35/35 个反向有害修复。
- 使用独立已知真值条款测试后，正确修复 35/35 通过，有害修复 35/35 被拒绝。
- v3 在当前保守作用域内覆盖 25 个同名行修改、domain 修改和 objective 修改；25/25 正确方向被枚举和恢复，25/25 反向修改被独立测试拒绝。
- 候选自身派生的测试会接受 25/25 个反向语义选择。它只能证明实现忠实于所选方向，不能证明所选方向正确。

这一区分改变了论文中的 gate 表述：求解器与候选测试是**执行一致性证据**；自然语言正确性仍来自语义审查，并必须在独立 formulation gold 上测量。

## 4. 阶段 1b：自然开发轨迹反事实

初始 v3 反事实把 2,695 个可比较响应编译为 370 个 repair，247 个通过数值／局部测试 gate；开发代理的已知转移为 3 次纠正、5 次退化，净值为 −2。进一步检查发现两种具体失败：

- teacher 使用不同的生成行名时，控制器把名称不匹配误解释为约束删除或新增；其中包括数学等价缩放和语义上不同的关系。
- 旧反馈的自然语言解释有时明确认为 initial 正确，却同时输出了指向 teacher 的 edit；v1 合同无法机器识别这种内部矛盾。

禁用未对齐行的增删候选并把每次目录限制为四项后，候选数从 771 降到 390，编译 repair 从 370 降到 256，通过 gate 的 repair 从 247 降到 158。开发代理转移缩小到 2 次纠正、2 次退化；去重后分别只涉及一个问题。该规则消除了由行名错位造成的已观察退化，但单审查仍没有正净效应。

v4 因此增加两个前瞻性控制：主审必须对目录中的每个候选显式选择 `initial`、`teacher` 或 `unclear`，避免“解释支持 initial、edit 却复制 teacher”的合同矛盾；第二个反方提示独立复核比例、等式／不等式、单位、变量域和代数等价性。只有两个审查都选择 teacher 的候选进入确定性 repair。两次审查来自同一基础模型，不能视为统计独立或语义证明；其作用是假设性的精度过滤，必须实测。

## 5. 阶段 2：v4 开发诊断（已完成并关闭）

候选集完全来自 `development_propose` / `development_select`，选择时只读取公开输入、冻结角色和历史可执行差异，不读取评价标签、参考答案或响应正文。每个 operational family 只取一个题目。严格行对齐后得到 12 个家族、12 道题，覆盖 IndustryOR、MAMO ComplexLP、NL4Opt 和 OptiBench；锁定测试题为 0。

冻结比较为 `Base` 对 `A-v4`，固定 replicate 17 和 65,536 trajectory token cap：

| 项目 | 上限 |
| --- | ---: |
| 推理单元 | 24 |
| 逻辑请求 | 60 |
| 无重试时唯一物理请求 | 48 |
| 含每请求最多三次尝试的物理上限 | 144 |
| 预留／服务商报告 token 总上限 | 9,500,000 |
| 单次最大输出 token | 8,192 |
| API 并发 | 5 |

API 固定为 AntChat `DeepSeek-V4-Flash`，无自动模型回退。运行具备 SQLite 账本、请求指纹去重、断点续跑、进度 JSON/HTML、单请求传输重试、单项耗尽后继续、连续传输故障熔断以及鉴权／模型／账本／预算全局停止。授权关闭后才加载开发评价参考并评分。

实际完成 24/24 个推理单元。47 个逻辑请求通过共享前缀复用为 35 次物理 API 尝试；没有重试、失败或熔断，账本记录 65,046 个预留或服务商报告 token。授权已关闭，不能用于后续调用。

11 题具有配对可判定代理：3 题两组都匹配，7 题两组都不匹配，0 次纠正，1 次退化。6 题产生候选目录，2 题形成双审查一致 repair 并实际改模。失败原因不是 API 或格式错误，而是语义机制：

- **封闭候选集错误**：铁路调车题的 initial 与 teacher 都遗漏正确的库存偏移，v4 只能二选一；两位审查者一致选择了仍然错误的 teacher 方向。
- **相关审查错误**：投资比例题要求部分量至少占总量的 40%，两位同源审查者都接受了把部分量直接与另一部分比较的错误代数式。
- **自证测试错误**：候选局部测试由 teacher 方向产生，所以只能证明 edit 执行了 teacher 的选择，不能证明该选择符合原文。

因此，预先固定的“纠正严格多于退化”条件未满足；没有扩大 API 范围。

## 6. 阶段 3：v5 独立语义合同

### 6.1 方法

v5 在 teacher 候选之外加入一个控制器拥有的 typed semantic contract 层。当前实现仅覆盖三类可机械约束的高置信语法：

1. `how many` 与模型接口中 `Number of ...` 的不可分计数对象，生成整数域合同；可分的 gallons、weight 和 money 明确弃权。
2. “某部分至少占总量 p%”，生成 `part - p * total >= 0` 的规范行，而不是从任一候选方向生成测试。
3. “地点 i 当前有 s、需要 d”与明确的有向流变量，生成 `inflow - outflow >= d-s`；若完整模型因此不可安全求解，回滚并报告接口不足。

合同只替换唯一对齐的既有 row/domain，不增加无关变量，也不读取参考答案。它在 workflow 前修复可确定的初始错误，并在后续 gate 中拒绝违反合同的 teacher proposal。未知语法保持未决。

### 6.2 开发结果

在 v4 的同一批 12 题上做零 API 回放：

| 版本 | 实际改模 | 纠正 | 退化 | 结果 |
| --- | ---: | ---: | ---: | --- |
| v4 双审查 | 2 | 0 | 1 | 未通过 |
| v5 合同回放 | 2 | 2 | 0 | 通过开发门槛 |

v5 将两个明确询问离散对象数量的问题改为整数域，阻止了比例约束退化；铁路调车题的正确流平衡与当前单向变量接口不相容，因此回滚为未决，没有把局部正确条款包装成完整正确模型。

为降低 12 题偶然性，随后对全部 150 条 development-propose/select 记录做同一冻结逻辑的回放。150 条中 38 条没有可支持模型，15 条触发合同，3 条安全改模；三条均从代理不匹配转为匹配，没有退化，涉及两个 operational family。该扩展仍是开发分析，不是独立确认。

### 6.3 冻结锁定评价

在打开锁定结果前，代码、输入、来源记录、评价器和成功条件被冻结为计划哈希 `fbda89c0815f14cd6484bbf17f58e77d25f80217ee4b59790276ef1130359320`。评价只复用既有 Base 轨迹，没有模型调用，也不输出逐题锁定成绩。

522 条锁定记录中，137 条没有可支持模型，13 条触发合同，10 条已合规，1 条接口不足，2 条实际改模。这两个改模来自同一 operational family：一个修改前后都匹配已发布标量代理，另一个代理不可判定；纠正和退化均为 0。因此预注册的“至少一次锁定纠正且零退化”条件未通过。

这不是正向确认，也不是观察到伤害。它说明当前 benchmark formulation accuracy 对某些结构变化缺乏辨别力，而且有效改模只有一个 operational family，统计功效不足。现有 13 个结构化参考都不覆盖这两个变化记录，不能补做独立 formulation 比较。

## 7. 论文框架中的位置

这组结果适合作为论文的机制诊断与方法修订部分：

1. **Failure Funnel Study**：量化从初始模型、可执行差异、反馈编译、实际改模到代理转移的信号衰减。
2. **Controller-Owned Evidence Compilation**：将哈希、引用偏移、edit 和测试点从生成模型移到确定性控制器。
3. **Correlated Review Failure**：展示两次同源审查会共享代数误解，一致性不是独立真值证据。
4. **Candidate-Independent Semantic Contracts**：将可证明的离散域、比例和流平衡语义编译成 controller-owned 规范约束及 fail-closed gate。
5. **Mechanism Evaluation**：先报告合成故障注入，再报告开发自然题的行动率与纠正／退化，最后报告冻结锁定集的低作用率和代理不可辨识性。
6. **Claim Boundary**：当前可以主张失败机制已被定位、机械转化率已提升、v5 在开发代理上消除了已观察回退并产生净纠正；尚不能主张锁定 benchmark 的 formulation accuracy 提升或 workflow evolution 有效。

论文中的核心研究问题应改写为：

- **RQ1**：可执行差异链路中的主要信号损失发生在哪里？
- **RQ2**：控制器拥有的证据编译能否提高可行动率？
- **RQ3**：候选独立语义合同能否降低同源 teacher 的错误接受？
- **RQ4**：在 formulation-level gold 上，合同修复是否真正改善语义正确性，而非只改变标量代理？
- **RQ5**：当动作与评价信号足够密集时，Full 是否优于简单 A+B？

下一步不能再用这批锁定代理调参。13 项、9 个 operational family 的无参考答案盲审包已经生成，其中包含 3 个候选变化对；A/B 顺序随机化，映射键与审查包分离。审核协议已冻结为 `experiments/v5_blind_semantic_audit_protocol.json`，协议哈希为 `80051814f52a944529dee322d90cb2a6af1a274f04db3e01ed53a1ade64bb826`。本地独立审核页面可逐项保存草稿并导出与当前 packet 哈希绑定的密封 JSON；页面不包含参考答案、映射键、原始题号或家族号。

目前没有真实审核答案。至少两名未参与方法设计的 OR 审核者应独立判断原文条款、变量域、规范行和完整模型，分歧由第三名不同审核者仲裁；评分脚本会拒绝相同审核者、旧 packet、不完整或未密封答案，并只输出不含 audit ID 的汇总。由于实际候选变化只有 3 对、至多覆盖 2 个 operational family，本轮只能作为机制审核和下一轮先导的前瞻性 gate，不能形成确认性效果声明。只有满足“合同判定无 incorrect、至少一个变化家族偏好合同候选、且没有变化家族偏好初始模型”的冻结条件后，才可设计未使用家族上的小型 `Base / A-v4 / A-v5` 诊断。任何新 API 范围必须另行授权。

可复现输出为 `results/mechanism_v2_offline_replay.json`、`results/mechanism_v2_synthetic_validation.json`、`results/v4_development_pilot_summary.json`、`results/mechanism_v5_offline_replay.json` 和 `results/v5_offline_frozen_evaluation.json`。v4 计划与关闭授权位于 `experiments/v4_development_pilot_plan.json` 和 `experiments/v4_development_pilot_authorization.json`；v5 冻结离线评价计划位于 `experiments/v5_offline_evaluation_plan.json`。盲审包、审核页面与映射键保存在忽略提交的 `results/private/v5_blind_semantic_audit/`；公开清单为 `results/v5_blind_semantic_audit_manifest.json`，冻结协议为 `experiments/v5_blind_semantic_audit_protocol.json`。

## 8. 阶段 4：v6 显式离散计数扩展

### 8.1 设计与安全边界

v6 保持已被 v5 计划和盲审协议绑定的 `semantic_contracts.py` 不变，在独立版本中扩展显式可数对象语法。新规则只有同时满足以下条件才生成整数域合同：题面以 `how many` 明确询问数量；模型接口以 `Number of ...` 声明对应业务变量；问题短语和变量含义共享白名单内的离散名词。新增类别覆盖 bag、bottle、can、day、experiment、package、process、ream 和 taco。gallons、kilograms、hours、dollars、hectares 等可分量继续弃权；没有明确问题或变量未声明为 count 时也弃权。合同仍只修改 domain，并要求完整模型求解成功，否则回滚。

该扩展来自开发轨迹中的低覆盖诊断；锁定块只在打开标签前用于无标签作用率检查。实现新增 `formal-runtime-v6`，v5 行为由回归测试保持不变。

### 8.2 开发回放

在固定的 150 条 development-propose/select Base 记录上，v5 与 v6 使用相同求解器和评价器：

| 版本 | 实际改模 | 代理纠正 | 代理退化 | 纠正家族 |
| --- | ---: | ---: | ---: | ---: |
| v5 | 3 | 3 | 0 | 2 |
| v6 | 6 | 6 | 0 | 5 |

v6 相对 v5 新增 3 个纠正家族，未观察到开发退化。由于词表和规则在查看开发结果后迭代，该结果属于事后机制证据，不能作为确认性估计。

### 8.3 冻结二次评价

在读取 v6 锁定结果前，代码、数据、评价器、作用队列和成功条件被冻结，计划哈希为 `57aa221cecb458bc2d60641e5c16af4ccca32b0ca80e0dccda9badcde1ee7b00`。无标签预检仅确认 12 个实际改模、覆盖 8 个 operational family。预设门槛要求：相对 Base 至少 3 次纠正、0 次退化、至少 2 个纠正家族；相对 v5 至少 1 次新增纠正且 0 次新增退化。

一次性聚合评价得到：12 个改模中，相对 Base 为 4 次纠正、7 次前后均匹配、1 次不可判定、0 次退化；相对 v5 的 10 个新增改模为 4 次纠正、6 次前后均匹配、0 次退化。纠正覆盖 3 个 operational family，冻结门槛通过。该结果没有新增 API 请求。

这是项目首次在冻结的锁定评价中观察到正向净变化。按“最终 objective/status 与公开答案一致”为 benchmark formulation accuracy 的操作定义，固定 522 条分母下净提高 4/522，即 +0.77 个百分点。记录级 4:0 不一致对的单侧精确概率为 0.0625，家族级 3:0 为 0.125；两者都不足以单独支持常规显著性结论，且该块此前已报告 v5 聚合结果。因此可报告“冻结二次评价中的方向性 formulation-accuracy 提升”，不可报告为新鲜独立测试上的统计确认。

## 9. 阶段 5：v7 双视角来源账本

### 9.1 设计动机与机制

v4 的主要失败是同一 backbone 的初始模型与审查者可能共享同一代数错误；v6 则安全但覆盖窄。v7 不再从初始模型和 teacher 二选一，而是从题面独立生成两个完整账本：一个按变量优先，一个按约束优先。两条提示都看不到 Base 模型。每个变量、目标项、约束、有限边界、右端项与非零常数都必须绑定题面中的精确引文和字符区间，所有数值必须在对应引文中出现。控制器验证 schema、规范顺序、引文位置、数值来源、稀疏行和完整模型可解性。只有两份规范模型完全一致时才接受，否则显式弃权。`FullV7` 在该共识模型上继续应用未修改的 v6 语义合同。

这一设计把错误相关性和开放式解释转化为可检测的双视角分歧，同时保持 fail-closed。它也允许在 Base 没有可用模型时恢复完整模型。开发阶段报告 `Base`、`V6`、`DualLedger` 和 `FullV7` 四组，分别估计已有合同、独立账本和二者组合的贡献。

## 11. 阶段 6：v8 Source-Indexed 数值编译

### 11.1 机制

v8 直接针对 Text2Opt 的 binding 失败。控制器先在公开题面中为每个数值出现位置生成稳定 ID、原始文本、规范值和字符区间；模型不再自行抄写数字或生成引文区间，而是输出带来源表达式的 MILP。每个有限边界、RHS、目标系数和非结构性行系数只能来自：单个数值 ID、符号取反、百分数转小数、或至多 64 个已引用数值的加减和。只有 `-1/0/1` 可作为无来源的代数结构常数。编译器重新计算全部数值，拒绝未知 ID、非百分数的百分比变换、未引用字面量、非法表达式和 schema 漂移，再由隔离求解器验证。辅助候选编译或求解失败时，`FullV8` 保留 Base。

这解决了 v7 中由模型生成字符偏移导致的主要机械失败，并把“所有数值来自题面”变成可执行不变量。它仍不能证明引用的数值被绑定到正确变量或正确约束，因此准确率必须由独立开发/确认评价测量，不能把编译成功当成正确。

### 11.2 分组数据隔离

新的公开输入分割在进一步读取答案前冻结为 70 条开发和 401 条确认。resource-allocation 沿用上游 train/eval；六个 template 类别各取五条作为开发，其余为确认。选择只使用题号、公开文本哈希和非结果规模元数据。`small_prose`、`small_capped` 等改写版本完全排除，避免母题与变体跨集合。上述两条人工暴露记录强制归入开发并明确披露。开发评价文件只投影已冻结 70 条的 solver status 和 optimum，不执行 gold program；推理完成检查点之后才允许加载。

## 12. 阶段 7：v9 可信公共文本编译器

### 12.1 设计

v9 将六类具有稳定表格接口的 Text2Opt 问题从自由生成改为可信编译：控制器仅依据公开文本标题识别类别，检查索引和表格形状，实例化固定 formulation，并通过有界精确算法求解。运输、修正版设施选址和灾害响应使用受控 LP/MILP；VRPTW 使用可行路线枚举加集合划分；JSSP 使用 Giffler--Thompson active-schedule 分支定界；RCPSP 使用完整模式枚举与析取图分支定界。识别、解析、编译或求解任一步失败均保留 Base。resource-allocation 不在支持范围内，也保留 Base。

该设计直接修复 v8 暴露的完整性问题：在支持范围内，变量与约束由审计模板完整生成，而不是由模型决定列出哪些关系。V9 仍然是选择性系统，不声称覆盖任意自然语言优化问题。

### 12.2 开发证据

按实例组冻结的数据划分包含 70 条开发记录和 401 条确认记录。六类结构化开发样本各 5 条，v9 对 30/30 条均复现发布目标值。在 v8 的同一十题 Stage 1 上，Base 为 5/10，v9 为 10/10，得到 5 次纠正和 0 次退化。上述结果只用于冻结方法和确认计划，不进入确认性效应估计。

### 12.3 独立确认

确认集的结果在 401 条推理检查点全部形成后才加载。最终续跑计划哈希为 `20f166269ad881b607607cc6d13db878ec80f5c30acbf50bc39da46613f3a81c`；续跑只恢复冻结检查点并补齐未完成请求，没有改变方法、提示、模型、数据、endpoint 或 gate。

一条 Base 请求基础设施不可用，得到 400 条配对记录，完整率 99.75%。Base 准确率为 200/400（50.00%），v9 为 259/400（64.75%），绝对提高 **14.75 个百分点**；59 次纠正、0 次退化，单侧精确 McNemar `p=1.7347e-18`，配对差值的条件精确 95% 区间为 12.96–14.75 个百分点。七类中六类提高、一类持平、零类下降。预注册的七项确认门槛全部通过。

V9 在 90/401 条上采用可信编译结果，其余 311 条保持 Base。全部运行合计 401 次物理尝试、0 次重试和 17,917,504 个 reserved-or-reported tokens。公开聚合见 `results/text2opt_v9_confirmation_evaluation.json`，论文级结果与边界见 `docs/V9_CONFIRMATORY_RESULTS.md`。

### 12.4 论文结论边界

现在可以报告：在冻结的 Text2Opt 独立确认集上，选择性可信编译相对同一 `gpt-6-luna` Base 显著提高 benchmark formulation accuracy。这里的 accuracy 操作性定义为最优状态与发布目标值一致；它不等价于完整语义等价。公开基准可能受预训练污染，六个结构化类别包含同类实例，手写模板限制了对未知 problem family 的外推，resource-allocation 因 fallback 而没有提高。论文主线应据此从“LLM 自我反馈必然修复模型”调整为“失败闭合的可信编译在可识别结构上提高最终建模准确率，而早期反馈与 provenance 机制揭示了为什么完整性约束是关键”。
